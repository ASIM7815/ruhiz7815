# RUHIZ Full Website Architecture And Implementation Blueprint

This document explains the complete architecture needed to turn RUHIZ into a full student collaboration platform where users create projects, other users request to join, project creators approve members, a private group is automatically available for approved members, and marketplace access remains separate from project membership.

The goal is not only to add missing pages. The goal is to make the website behavior complete, secure, consistent, and easy to maintain.

## 1. Product Vision

RUHIZ is a student collaboration platform with these core areas:

- Projects: students create project ideas and form teams.
- Project groups: each project has a private group/chat/workspace.
- Join requests: users request access and the project creator approves or rejects.
- Messages: direct messages and project group messages.
- Knowledge hub: students share learning resources.
- Study groups: students join learning groups.
- Startups: students create founder/team opportunities.
- Marketplace: students buy, sell, or offer services, but marketplace permissions must be separate from project permissions.
- Notifications: users receive updates when important actions happen.
- Admin/moderation: platform admins manage users, content, reports, and permissions.

## 2. Current Repo Snapshot

The app already has a good base:

- Next.js app router structure under `src/app`.
- Route groups: `(marketing)`, `(auth)`, and `(platform)`.
- Supabase auth helpers.
- Prisma schema for users, projects, project members, join requests, listings, resources, study groups, startups, notifications, and direct message-related data.
- Supabase SQL for group conversations, group participants, and group messages.
- Project creation API.
- Project join request API.
- Join approval API.
- Group list, detail, members, messages, and leave APIs.
- Marketplace listing APIs.
- Direct messaging UI and group chat UI.

Important current issue:

- Project membership is stored in Prisma tables.
- Project group chat membership is stored in Supabase group tables.
- Project creation currently adds creator as a project member, but the project group is only created during join approval if missing.
- Notifications page is mostly static/empty.
- Marketplace is available in platform navigation for every logged-in user.
- Workspace page currently contains placeholder arrays and mock members.

The implementation should unify these behaviors so every project has a real group from creation time, every permission is checked server-side, and every page reflects live data.

## 3. Architecture Principles

Use these rules throughout the implementation:

- Server-side permission checks are mandatory. Frontend hiding is not security.
- Every project must have exactly one default project group.
- The project creator is always the initial project admin.
- A user cannot access a project group unless they are an approved project member or project admin.
- Join requests must have a clear status lifecycle.
- Marketplace access must not come from project membership.
- Database constraints should prevent duplicate membership, duplicate requests, and duplicate group participation.
- UI state should come from API state, not hardcoded assumptions.
- Notifications should be generated by backend actions, not by frontend-only logic.
- Prefer one source of truth for membership and permissions.
- Every write action should be auditable enough to explain who did what.

## 4. Recommended Data Ownership

The cleanest design is:

- Prisma/Postgres is the source of truth for business data.
- Supabase Auth is the source of truth for login identity.
- Supabase Realtime is used for live message subscriptions.
- Google Cloud Storage is used for uploaded files.

Because group chat currently uses Supabase tables directly, there are two acceptable implementation paths.

### Recommended Path

Add group conversation models to `prisma/schema.prisma` and manage group conversations through Prisma as well.

Supabase Realtime can still subscribe to the same Postgres tables. This keeps a single database and a single schema definition.

Benefits:

- Easier transactions.
- Easier migrations.
- Easier permission checks.
- Less mismatch between Prisma project members and Supabase group participants.

### Acceptable Short-Term Path

Keep group tables in Supabase SQL, but create helper services that always update Prisma membership and Supabase group participation together.

If this path is used, every project creation, join approval, member removal, and project deletion must call one shared service instead of duplicating logic inside API routes.

Use permission helpers instead of scattering checks through routes.

Recommended helper functions:

- `requireAuth()`
- `requirePlatformAdmin(user)`
- `canViewProject(user, project)`
- `canEditProject(user, project)`
- `canRequestProjectJoin(user, project)`
- `canApproveProjectJoin(user, project)`
- `canAccessProjectGroup(user, group)`
- `canManageGroupMembers(user, group)`
- `canSendGroupMessage(user, group)`
- `canAccessMarketplace(user)`
- `canCreateMarketplaceListing(user)`
- `canManageMarketplaceListing(user, listing)`

Permission table:

| Action | Guest | Logged-in user | Pending requester | Project member | Project admin | Platform admin |
| --- | --- | --- | --- | --- | --- | --- |
| View public project | Yes | Yes | Yes | Yes | Yes | Yes |
| Create project | No | Yes | Yes | Yes | Yes | Yes |
| Request to join open project | No | Yes | No duplicate | No | No own project | Yes |
| View join requests | No | No | No | No | Yes | Yes |
| Approve/reject join request | No | No | No | No | Yes | Yes |
| View private group | No | No | No | Yes | Yes | Yes |
| Send group message | No | No | No | Yes | Yes | Optional |
| Remove group member | No | No | No | No | Yes | Yes |
| Access marketplace browse | Product policy | Product policy | Product policy | Product policy | Product policy | Yes |
| Create marketplace listing | No | Only seller role | Only seller role | Only seller role | Only seller role | Yes |

Important marketplace rule:

- Do not use project role to decide marketplace access.
- Use `marketplaceRole`, `marketplaceStatus`, or a dedicated permission table.

## 7. Core User Flows

### Project Creation Flow

Expected behavior:

1. User logs in.
2. User creates project.
3. Backend validates title, problem, description, skills, max members, and status.
4. Backend creates project.
5. Backend creates creator's `ProjectMember` row with role `ADMIN`.
6. Backend creates project group automatically.
7. Backend creates creator's `GroupParticipant` row with role `ADMIN`.
8. Backend returns project ID and group ID.
9. User is redirected to project overview or workspace.

Critical implementation detail:

- Steps 4 to 7 should happen in one database transaction if group tables are managed by Prisma.
- If using Supabase direct calls separately, create a repair job or retry helper so projects cannot remain without a group.

### Join Request Flow

Expected behavior:

1. Logged-in user opens a project.
2. UI shows correct state:
   - Owner: `Your Project`
   - Member: `Open Workspace`
   - Pending: `Request Pending`
   - Rejected: `Request Rejected` or `Apply Again`
   - Not requested: `Apply to Join`
3. User sends optional message.
4. Backend validates project is joinable.
5. Backend creates `ProjectJoinRequest` with status `PENDING`.
6. Backend creates notification for project admin.
7. Project admin sees request in project admin area.

Missing current behavior to add:

- A normal user should be able to know their own request status. Current owner-only join request GET is not enough for the project detail page.

Add endpoint:

- `GET /api/projects/[projectId]/join/status`

Response:

```json
{
  "relationship": "NONE | OWNER | MEMBER | PENDING | REJECTED",
  "requestId": "optional",
  "canRequest": true
}
```

### Join Approval Flow

Expected behavior:

1. Project admin opens project requests page.
2. Admin approves or rejects request.
3. Backend verifies current user is project admin.
4. Backend verifies request belongs to project and is pending.
5. If rejected:
   - update request status to `REJECTED`
   - set `reviewedBy`
   - set `reviewedAt`
   - notify requester
6. If approved:
   - check project capacity
   - update request status to `APPROVED`
   - add project member
   - add group participant
   - notify requester
7. Approved user can immediately enter the group/workspace.

Important rule:

- Approval must fail safely if the project is full or the user is already a member.

### Group Access Flow

Expected behavior:

1. User opens `/projects/[projectId]/workspace` or `/messages?group=...`.
2. Backend checks active group participation.
3. If active, return group details and messages.
4. If not active, return 403.

The frontend may show friendly states, but backend remains the final gate.

### Member Removal Flow

Expected behavior:

1. Project admin removes a member.
2. Backend verifies admin permission.
3. Backend prevents removing the last admin unless ownership is transferred.
4. Backend marks project member as removed or deletes membership based on policy.
5. Backend removes/deactivates group participant.
6. Backend creates notification for removed user.
7. Removed user loses access immediately.

### Marketplace Access Flow

Expected behavior:

1. User opens marketplace.
2. Backend checks marketplace permission.
3. If user can browse, return listings.
4. If user cannot access, show restricted access page.
5. Creating listing requires seller permission.
6. Platform admin can approve, hide, remove, or suspend listings.

Missing current behavior to add:

- Marketplace route and API currently allow normal logged-in users.
- Add backend permission checks to marketplace API.
- Hide or disable Marketplace navigation based on marketplace permission.

## 11. Service Layer Architecture

Add a thin service layer under `src/lib/services` so API routes stay simple.

Recommended files:

```txt
src/lib/services
  projects.ts
  join-requests.ts
  groups.ts
  notifications.ts
  marketplace.ts
  uploads.ts
  permissions.ts
  audit-log.ts
```

Responsibilities:

- `projects.ts`: create/update/archive projects, enforce owner/admin rules.
- `join-requests.ts`: create request, approve, reject, cancel.
- `groups.ts`: create group, sync participants, send system messages.
- `notifications.ts`: create and list notifications.
- `marketplace.ts`: enforce seller/buyer/admin logic.
- `uploads.ts`: enforce upload ownership and file metadata.
- `permissions.ts`: centralized permission checks.
- `audit-log.ts`: record important admin/moderation actions.

Important:

- Do not duplicate join approval logic in multiple API routes.
- Do not let frontend call separate APIs that can create inconsistent state.
- One product action should map to one server-side service method.

## 16. State Machines

### Project State

```txt
DRAFT -> OPEN -> IN_PROGRESS -> COMPLETED -> ARCHIVED
DRAFT -> ARCHIVED
OPEN -> ARCHIVED
IN_PROGRESS -> ARCHIVED
```

Rules:

- Only admins can change project state.
- `OPEN` allows requests.
- `IN_PROGRESS` may allow requests only if team has capacity and admin enables it.
- `COMPLETED` should normally block new join requests.
- `ARCHIVED` blocks new activity except admin restoration.

### Join Request State

```txt
PENDING -> APPROVED
PENDING -> REJECTED
PENDING -> CANCELLED
PENDING -> EXPIRED
REJECTED -> PENDING only if reapply is allowed
```

Rules:

- Only requester can cancel.
- Only project admin can approve/reject.
- Approval creates membership and group participation.

### Marketplace Listing State

```txt
DRAFT -> ACTIVE
ACTIVE -> SOLD
ACTIVE -> HIDDEN
ACTIVE -> UNDER_REVIEW
UNDER_REVIEW -> ACTIVE
UNDER_REVIEW -> REMOVED
HIDDEN -> ACTIVE
```

Rules:

- Seller can edit own draft/active listings.
- Admin can hide/remove/review any listing.

## 17. Security Requirements

Must-have checks:

- Every protected API calls `requireAuth`.
- Every project edit verifies project admin.
- Every join approval verifies project admin.
- Every group message read/write verifies active group participant.
- Every media upload verifies user can upload to that entity.
- Every marketplace create/update verifies seller permission.
- Every admin route verifies platform admin/moderator.
- Never trust `userId`, `role`, or `ownerId` sent from the client.
- Do not expose service-role Supabase keys to client code.

Data privacy:

- Pending users cannot see private group messages.
- Rejected users cannot see group messages.
- Removed users cannot see old group messages unless product explicitly allows archived read access.
- Non-admin members should not see private approval messages unless needed.

Rate limits to add later:

- Join request creation.
- Message sending.
- File uploads.
- Marketplace listing creation.
- User search.

## 27. Final Target Behavior

The complete website should work like this:

```txt
User creates project
  -> project is saved
  -> project group is automatically created
  -> creator becomes project admin
  -> creator becomes group admin

Another user requests to join
  -> request is pending
  -> creator receives notification
  -> requester cannot access group yet

Creator approves request
  -> request becomes approved
  -> requester becomes project member
  -> requester becomes group participant
  -> requester receives notification
  -> requester can open workspace and message

Marketplace
  -> remains separate
  -> project membership does not grant seller access
  -> seller/admin permission controls listings
```

That is the architecture needed to make RUHIZ feel like a complete, secure, production-ready collaboration website instead of separate unfinished screens.
